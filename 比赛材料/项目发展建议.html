壹

现状盘点

CODE AUDIT · WHERE WE ARE

对仓库逐文件审计后的结论：这个项目比你们自己以为的更完整——但它是一座"建好了展厅、却没开门"的博物馆。

已经建成的，是真资产

Heritage-Foundry（非遗造物局）不是半成品。它已经跑通了一条完整的产品闭环： 18 项非遗技艺浏览 → Gemini AI 生成文创图 → Three.js 3D 载体实时贴图 → Oklab 色差拼豆图纸 → Supabase 作品保存。 首页的粒子 morph 博物馆（5 万粒子在 18 件文物模型间形变）在视觉上已经具备"高端精致"的底子，这正是用户体验创新方向的第一评分关键词。

01
18 项技艺数据

craftData.js 结构化故事卡：苗绣、剪纸、唐卡、陶瓷、云锦……每项含 story / 模型 / 图标

02
420MB GLB 模型

18 件展品级模型，Git LFS 管理——AR 化最重的资产已经提前备齐

03
Prompt 工程库

15 技艺 × 10 IP × 5 载体 × 8 风格的导演式 prompt 模板，服务端二次增强

04
拼豆算法

图像 → 18×12 图纸 → Oklab 感知配色 → 材料清单，独家记忆点

05
降级容错

无 Gemini / 无 Supabase 均可启动并明确报错，演示稳定性有保障

但四个缺口，个个致命

GAP 01

零 AR / 零鸿蒙

全仓库无一行 WebXR、AR Engine、ArkUI 代码。3D 场景全部是"模型居中 + 轨道相机"的展示型组织，与 AR 需要的"真实尺度 + 平面锚定"范式不兼容——展示层必须重做，但数据层 100% 可复用。

GAP 02

首屏 ≈ 90MB

71MB 未子集化字体 + 14.7MB 首个 GLB + 4.5MB 首页配图 + three.js。切一件展品重新下载最大 63.8MB 模型，无 DRACO/KTX2 压缩、无缓存。"用户体验"赛道上，加载慢就是原罪。

GAP 03

没有部署形态

Express 不托管前端产物，无 Dockerfile、无 CI、无 LICENSE、CORS 全开。生图 API 无鉴权无限流——公开部署即烧钱。初赛要交演示链接，这条现在是空的。

GAP 04

数据三处漂移

同一项非遗的名称/故事在 craftData.js、apiService.js、promptService.js 各存一份，craft 映射表重复两份。加新品类要改三个地方，复赛迭代时一定会出 bug。

结论：数据层与算法是宝，展示层要重做，性能是生死线，部署是入场券。 —— 代码审计总结，详见附录引用文件

三条必须接受的赛制现实

现实一

初赛拼的是文档，不是代码

线上评审 + 报名队数庞大，刘宇轩在群里的判断大概率是对的：初筛高度依赖文本材料（很可能有 AI 辅助审阅）。创意书的结构完整度与关键词覆盖率，直接决定能否进复赛。代码可以只有 demo，文档必须是满分作文。

现实二

鸿蒙特性是显性加分项

这是华为承办的鸿蒙赛道。评委想看到的是"这个体验为什么必须在鸿蒙上发生"——分布式协同、一次开发多端部署、元服务、小艺，每个被自然用上的鸿蒙能力都是得分点。硬凑会被看穿，但我们的多设备场景是真的合理（见第叁章）。

现实三

"用户体验"赛道的对手不是工程师

这个方向的强队往往是设计驱动的队伍。技术深度不是第一评分项——视觉完成度、交互自然度、故事感染力才是。这恰好是我们的主场：粒子博物馆首页 + 拼豆手作闭环，比绝大多数"套壳 AI 聊天"项目更有体验纵深。

叁

产品定位

WHAT TO BUILD

会议定的方向（非遗 × 流行 IP × AR × 鸿蒙协同）是对的。现在需要把它收敛成一句评委 10 秒能记住的话、一条三分钟能演示完的故事线。

「遗见」—— 把非遗博物馆放进每个人的客厅。 定位建议：AR 非遗数字博物馆 × AI 文创共创平台。名字可再议，但"走出展柜"这个意象建议保留，它是路演的第一张幻灯片。

三分钟演示故事线（评委视角）

幕一 · 见
文物走出展柜

打开手机摄像头，一件苗绣绣绷 / 景德镇瓷瓶以真实尺寸落在你家茶几上，可环绕观看、可放大看针脚

幕二 · 懂
点读文化卡片

点击模型热点，弹出这项技艺的故事卡：它从哪来、谁在做、为什么快要失传

幕三 · 创
AI 文创共创

选一件流行 IP 与技艺碰撞，AI 生成帆布包/手机壳设计图，实时贴到 3D 载体上预览

幕四 · 作
图纸变成实物

一键生成拼豆图纸 + 材料清单——屏幕上那件文物，周末就能拼出来挂在包上

幕五 · 传
多设备共赏

手机看到一半，流转到平板继续设计；成品投上智慧屏，全家人围看——鸿蒙分布式在此自然发生

为什么是这条线：三个差异化支点

支点 1 · 体验

闭环，而非展示

市面 AR 博物馆（含会议参考的小红书案例）止步于"看"。我们是唯一一条「看 → 懂 → 创 → 作 → 传」的完整链路——评委记住的是那个"AI 图 30 秒变成能拼出来的拼豆图纸"的瞬间。

支点 2 · 技术

鸿蒙协同有真场景

手机 AR 受屏幕尺寸限制是真实痛点 → 流转到平板/智慧屏是真实解法。这不是硬凑鸿蒙特性，而是"只有分布式才能做好"的体验，恰好命中赛道口味。

支点 3 · 立意

公益叙事可讲大

非遗传承人老龄化、年轻群体触达难是真问题。"让年轻人先在家里爱上文物，再走进真的博物馆"，社会价值线与商业价值线（文创定制）都讲得通，答辩时站得住。

克制清单：这些先不做

电商交易、用户账号体系、UGC 社区、更多 IP 扩充——全部砍掉或写进"未来规划"。三个人、十天初赛、两个月复赛，把五幕故事线打磨到惊艳，比把功能列表写满更有杀伤力。DESIGN.md 里的 Non-goals 已经说得很对，坚持它。

肆

技术路线

HOW TO BUILD IT

原则只有一条：数据层全保留，展示层渐进重做，鸿蒙化选阻力最小的路径。不重写 promptService、patternGenerator、craftData——这些是花了两周攒下的壁垒。

4.1 AR 方案选型（绵阳的调研题，这里有参考答案）

会议留了"VR 还是 AR"的开放题。答案明确是 AR：VR 需要头显（评委没有），AR 用评委自己的手机就能体验。具体三条路径对比：

方案成本效果风险适用阶段
① Web 端 AR
<model-viewer> / WebXR		 2–3 天出 POC，复用现有 GLB 与 GLTFLoader 管线 安卓走 ARCore / WebXR，iOS 走 AR Quick Look，浏览器直达，扫码即体验 鸿蒙 Next 浏览器兼容性需实测；能力受 Web 限制 初赛 Demo + 复赛主力
② 华为 AR Engine 原生
ArkTS		 1–2 周起，需学 ArkUI 与 AR Engine API 平面检测/光照估计更稳，鸿蒙叙事满分 团队无华为实体机；模拟器对 AR 支持有限，需云真机 决赛冲刺期的"杀手锏"
③ 商用 SDK
8thWall 类		 接入快但收费 成熟稳定 付费 + 与"鸿蒙原生"叙事冲突 不建议

建议节奏：初赛用 <model-viewer> 包一层现有展品页，录一段"瓷瓶落在桌面上"的 15 秒视频放进创意书——成本一个下午，说服力胜过十页文字。复赛把 AR 页做成独立入口，模型走压缩后的管线。决赛前评估 AR Engine 原生版本，作为现场答辩的差异化演示。

4.2 鸿蒙适配：选"混合壳"，别重写

路径工作量体验结论
纯 ArkWeb 容器套壳极小（1–2 天）取决于 Web 性能可作复赛底线：能装到鸿蒙机上跑起来
混合：原生壳 + Web 内核中（1–2 周）导航/相机/流转用原生能力，生成页复用现有 Web推荐：ArkTS 原生首页 + AR 入口 + 跨设备流转按钮，crafts/generator 页走 ArkWeb 复用
全量 ArkTS 重写大（1 个月+）最佳团队时间与人力不允许，放弃

鸿蒙加分功能的落地优先级：① 跨设备流转（手机→平板继续浏览，鸿蒙分布式能力的招牌场景，演示效果直观）→ ② 元服务卡片（桌面卡片直接展示"今日文物"，轻量化触达）→ ③ 小艺语音唤起（"小艺小艺，看看苗绣"）。做一个就够写进文档，全做是决赛水平。

4.3 性能优化：用户体验赛道的生死线（按 ROI 排序）

  • GLB 模型压缩管线

    18 个模型共 420MB 全部走 gltf-transform / gltfpack：DRACO 或 meshopt 几何压缩 + KTX2 纹理压缩，预期降到 40–80MB（约 1/10）。这是 AR 移动端可加载的前提，不做这个 AR 无从谈起。

    收益：展品切换从 30 秒级 → 秒开 · 成本：半天（写个批量脚本）
  • 字体子集化

    思源宋体 ×2 + 霞鹜文楷共 71MB，全量字体内 99% 的字永远用不到。用 fonttools/pyftsubset 按实际文案子集化，预期 < 2MB。

    收益：首屏 −69MB · 成本：1 小时
  • 首屏分包与懒加载

    首页只预载首个展品模型（压缩后 ~2MB），其余 17 个空闲时预取；museum-bg 等大图转 WebP/AVIF；three.js 已独立 chunk，保持。

    收益：首屏 ≈90MB → 5MB 内 · 成本：半天
  • 图像存 Supabase Storage，不入库

    当前作品图以 base64 直接写进 image_url 文本列（单条 1–2MB），列表查询会越来越慢。改存 Storage 只存 URL。

    收益：作品列表不随时间劣化 · 成本：2 小时
  • 部署与工程化

    前端 Vercel/华为云 CDN，Express 加 static 托管 dist 或用华为云 ECS/函数工作流；补 Dockerfile + GitHub Actions（lint+test+build）；补 LICENSE；生图 API 加简单频次限制。

    收益：有可交的演示链接 · 成本：1 天

4.4 架构上的小修（复赛迭代前做掉）

把 craftData.js 提升为唯一数据源，apiService.getCraftInfo 与 promptService.CRAFT_LIBRARY 改为从它派生；home.js 与 crafts.js 重复的 craft 映射表合并。半天工作量，换复赛两个月不加新 bug。

风险与对策

RISKS & MITIGATIONS

按发生概率 × 杀伤力排序，每条都有具体对策，没有"到时候再说"。

RISK 01 · 高

团队无华为实体机

对策：DevEco Studio 模拟器调 UI 与流转逻辑；华为云远程真机（云调试）做关键验证；文档与视频中的"真机画面"可用模拟器 + Web 端演示组合呈现。10 月前如晋级，再考虑借/购一台二手鸿蒙设备。

RISK 02 · 高

WebXR 兼容性碎片化
